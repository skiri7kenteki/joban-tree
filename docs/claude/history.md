## 基本の使い方（段階16 までの目標。段階17〜の方針で置きかわった）
1. 棋譜を貼り付ける（または盤上で手を進める）
2. 研究したい局面を選ぶ
3. 「ふつう（2分）」で作るを押す（v0.4.0 で「さっと」はやめた）
4. 枝が増えていく様子を見ながら、途中で止めてもよい
5. 盤面と候補手リストでツリーをたどる。気になる枝は「ここから展開」で深掘り
6. 保存する。KIF で書き出して他のアプリ（iShogi など）に渡す

  スマホ縦では盤・‹ ›・手順の行がスクロールせずに見える（`measureFitAbove`）。
  「この研究手順を復習」「この局面からツリーを作る」（`src/app/handoff.ts` で新しいツリーの画面に手順・今の局面・自分の側・戦型を渡す）、
  「ツリーで見る」（今の局面までの平手からの手順が「ツリーの prefix＋ツリーの中で最後までたどれる手順」とまったく同じツリーがあるときだけ。`pathInTree`。
  `#/tree/<id>/study/<sid>/<手数>` でその局面をパンくずリストごと開く。複数なら選ぶ窓）、⋯ に 名前・メモを直す／KIF をコピー／ファイルで渡す（JSON・KIF）／消す（確認あり）

## 手順を編集する（段階9-1。段階10-2 で片付けた）
- **（段階10-2 で片付けた）手順を編集する（段階9-1、v0.20.0〜、持ち主の判断 2026-11-18「おすすめの通りで」。計算は `src/tree/studyEdit.ts`、編集中の下書きは `src/app/studyEdit.ts`）**：
  - 研究手順の画面の「手順を編集」→ 編集モード（`#/study/<id>/edit`。見出しを色付きの帯「✎ 手順を編集中」、左に「やめる」、右に「保存」）。**ふだんの盤は表示専用**、編集中だけ盤で指せる。保存するまで研究手順は書き換えない
  - 編集に入るときは今見ている局面のまま。編集中は 復習・ツリーを作る などのボタンとメモを隠し、「↶ 1手戻す」「ここで終わりにする」と案内の 1 行。スマホ縦ではこの 2 つのボタンの行までスクロールせずに見えるよう盤を縮める
  - 終わりの局面で指す → 最後に足す。途中の局面で次の手と同じ手 → 1 手進むだけ。違う手 → 窓で「ここから先を置き換える（後ろの n 手を消す）」「分かれる手として、別の研究手順にする」「やめる（指さなかったことにする）」
  - **別の研究手順にする**：その場で作って保存し、その編集へ移る（「別の研究手順を作りました：『名前』」）。手順は今の局面まで＋指した手、名前は初期値（分かれ目の手がわかる形）、メモは空、自分の側と戦型は元から（戦型が当てはまらなければ手順から）。
    元の研究手順にまだ保存していない変更があれば一緒に保存する（窓に一言）。同じ手順がすでにあれば作らずに知らせ「『X』の編集に移る／やめる」
  - ここで終わりにする：確認の窓（後ろの n 手を消す）。初期局面では押せない（手が 0 本になるため）。1 手戻す：最後の操作（足す・置き換える・終わりにする）を 1 つずつ取り消す
  - 保存：手が 0 本は保存できない（戦型の出発点で終わる研究手順は保存できる）。**ほかの研究手順とまったく同じ手順なら保存しない**（「編集に戻る／『X』を開く（この変更は捨てる）」）。
    手順が変わったら、戦型はいちばん長く一致する戦型に付け直し（無ければ外す。一覧のグループが変わることがある）、名前は初期値のままなら新しい手順の初期値に付け直す（自分で付けた名前は変えない）。メモはそのまま
  - やめる：変更があれば確認してから編集前に戻す。**スマホの戻るボタン**で編集から出たら、変更があれば「変更を捨てますか？」（編集に戻る／捨てる）。研究手順の画面以外へ移ったら下書きは捨てる
  - 復習の記録は直さない（記録は「局面＞正解の手」ごと。消した手の記録は出題に使われないだけで害はなく、同じ手を足し直せばまた使われる）

### 22-2 合わせて取り込む
- 設定の「データ」に［ほかの端末のバックアップを合わせる］→ ファイル → 確認の窓（種類ごとの 足す・新しくする・消す、消える研究手順の名前）→［合わせる］。両方そろえる手順を画面に 1 行
- 合わせる前のデータは「戻す」と同じく端末に取っておく。今の「戻す（全部置きかえる）」は残す。ツリーの生成中は合わせない
- バックアップは `version` 1 のまま、`data` に `deleted`（消した記録：種類・id か手順・日時。名前と形は任せる）を足して `KNOWN_KINDS` に。DB の版は設計案では「保存場所とバックアップの版は変えない」と伝えた（消した記録の置き場所はこれを守る形にする。守れなければ相談）
- 研究手順：**先に id、次に手順（moves）と自分の側で見分ける**
  - 同じ id で手順が違う：一方が他方の続き（または短くした形）なら、**後で手順を変えた方**の手順（任意の項目「手順を変えた日時」。無ければ `updatedAt`）。**別々に枝分かれしていたら両方残す**（一方に新しい id。消した枝が別の研究手順として戻ることがあるが、消えるより安全）
  - 名前・メモ・戦型は `updatedAt` が新しい方、作った日時は古い方
  - 手順と側が同じで id が違うものは 1 本に。**残す id は、作った日が古い方**（全部の端末で同じになる。同じ日時なら決まった順）。もう一方の id を指す稽古の記録は付け替える
- 局面の記録：**局面メモと候補の表は別々に新しい方**（別々の日時を任意の項目で）。表は手ごとに合わせる（細かい決まりは任せる）
- 稽古の記録：研究手順ごとに `lastAt` が新しい方。実戦の棋譜・戦型・ツリー・復習の記録：無いものは足す・あれば新しい方。実戦は同じ中身（`sameGame`）を 1 局に。設定（`prefs`）は合わせない
- 消した記録：消した日時が相手の最後に直した日時より新しければ消す。**90 日で捨てず、残し続ける**
- **取り消し・戻す**：復活させたものには「戻した日時」（任意の項目。`updatedAt` は変えない＝並び順はそのまま）を付けて、消した記録より勝つ。自分の消した記録は消す。［戻す前のデータに戻す］［戻す］で戻したものも同じ。相手から足された分は次の同期でまた入る（画面に書く）

### 22-3 Google ドライブで同期
- 押したときだけ。読む → 2 の決まりで合わせる → 書き戻す。同期の前のデータは端末に取っておく。最後に同期した日時を設定に。前の同期から 1 日以上なら設定と定跡帳のタブに一言。オフライン・ログイン切れ・エラーは理由を短く出してデータを変えない
- 範囲は `drive.appdata`。自前のサーバー・Google の JavaScript・CDN・ライブラリは使わない。REST API を `fetch`。service worker はドライブの通信をキャッシュしない（今は別オリジンをそのまま通す）
- **ログインは、ブラウザだけの画面移動の方式（`response_type=token`）**。Google の公式資料では古い方式扱い（持ち主は承知の上で選んだ）。長く使える鍵は持たない。鍵は端末の中だけ（バックアップに入れない）
  - 戻ってきた `#access_token=…` は、アプリの `#/…` の道順より先に受け取って URL から消す。`state` を確かめる
  - **最初にログインだけを作り、持ち主の実機（iPhone のホーム画面のアプリで戻れるか）で確かめてから続ける**
- **公開設定は「本番」**（依頼書の「テスト中」から変更）。審査を求められたら止めて相談。開発用の URL は足さない
- **同期ファイルは端末ごとに 1 つ**（各端末は自分のファイルだけを書き、全部を読んで合わせる）。中身はバックアップと同じ形。`prefs` は合わせない
- 持ち主の準備の手順書 `docs/google-drive-setup.md`（初心者向け）。クライアント ID はコードに書いてよい
- **CLAUDE.md を直す**：「データは端末の外へ送らない」「サーバー・ログインは作らない」「やらないこと」に例外＝持ち主が［Google ドライブで同期］を押したときだけ、持ち主自身の Google ドライブへ送る。ログインは Google のものだけ

### 依頼の文
重要な前提：現在の盤の大きさには不満がないため、盤のサイズ・配置は基本的に変更しない。今回の改善対象は、盤の直下にある研究候補一覧とする。

通常表示：候補行には以下だけを表示する。
- 指し手（最も大きく表示）
- 研究手順名
- 必要に応じて本線・次善などの札

評価値・読み筋・局面メモなどの詳細情報は通常表示しない。

操作：
- 候補行をタップすると、その研究手順を盤に表示する。
- 詳細情報を確認する操作は別に設ける。
- 詳細操作は小さなボタンまたは既存の詳細メニューから行えるようにする。
- 候補行全体をタップ可能にする。
- 詳細ボタンのタップで候補行の選択操作が誤って発生しないようにする。

デザイン：
- 指し手は大きく、太めにする。
- 研究手順名は一段小さく、補足情報として表示する。
- 本線などの札は控えめにする。
- 選択中の行は木の茶色で控えめに強調する。
- 白いカードと明るい対局室のテーマを維持する。
- 盤のサイズは現在のまま維持する。

既存の研究の合流・手順前後・候補の分類などの機能は変更しない。

## 段階25：横歩取り以外の棋譜を戦型ごとに分ける・まとめて消す（依頼と、決まったこと）（2026-11-26〜27。段階を締めたときに docs/claude/stage25.md から移した）

1. 変化付き KIF で横歩取り以外（角換わりなど）を取り込むと、戦型を選べず「その他」に入る

### 原因（クラウドの Claude がコードで確かめたこと）
- 戦型は同梱の横歩取り 7 つと自分で登録した戦型だけ。グループは手順がどの戦型で始まるかで開くたびに決まる（`groupStudies`・`studyGroupKey`）。どれにも当てはまらなければ「その他」

- 戦型は「取り込みの確認画面で選ぶ・作る」と「定跡帳の ⋯ から登録」の両方
- まとめて消すのは「取り込み直後の［取り消す］」と「研究手順の一覧で選んで消す」の 2 つ（取り込みごとの記録を持たせる案・定跡帳を丸ごと消す案はとらない）

### 25-1 戦型を選ぶ・作る
- 取り込みの確認画面：自分の側の近くに「戦型」の行。自動で決まった戦型（全部が通る・側が同じ・いちばん長い）、無ければ「その他」
- 押すと窓：［今ある戦型から選ぶ］（取り込む手順が全部その戦型の手順で始まるものだけ）／［新しい戦型を作る］
- 新しい戦型：名前・グループ（今あるグループからも選べる）・出発点。出発点の初期値はチェックの付いた手順が**全部通る最後の局面**。本譜の上で ‹ › で動かせる（初期局面より後、全部が通る局面まで）。名前の初期値は「n手目 ▲７六歩まで」
- 登録は「n 本を取り込む」を押したとき（やめたら登録しない）。同じ手順の戦型があればそれを使う（`findSameMoves`）。戦型の `mySide` は取り込みの自分の側
- 定跡帳の ⋯「この局面を戦型として登録」：今の盤の局面までの手順で `RegisterTemplateDialog`（側は定跡帳の側）。「その他」から開いていたときは、登録後にその戦型の定跡帳へ移るか聞く

### 25-2 まとめて消す
- 取り込み後の知らせに［取り消す］。確認（「取り込んだ n 本を消します」）→ **その取り込みで新しく足した分だけ**を消す。一緒に作った戦型も消すかは設計案で相談
- 研究手順の一覧に「選んで消す」：行にチェック、全部選ぶ／外す、下に固定の「n 本を消す」（確認に本数）。盤の取り消しの記録を捨てる決まりを守る
- 消した記録は 1 本ずつ（`src/tree/deleted.ts`・`src/storage/deleted.ts`）。稽古の記録の扱いも 1 本ずつ消すときと同じ。保存は 1 回のまとめ書き

### 確かめること
- Vitest：選んだ・作った戦型が `templateId` とグループに入る／出発点の初期値／「その他」の研究手順が登録後に新しいグループへ移る／［取り消す］が新しく足した分だけ消す／まとめて消したときの消した記録
- Playwright：角換わりなどを取り込み新しい戦型を作る → 定跡帳のタブに新しいグループの行／直後の［取り消す］で元の本数／一覧で 3 本選んで消す
- `studies.md`・`templates.md`・`book.md` を直す

### 了承した判断（2026-11-26「おすすめの通りで」）
1. ［取り消す］は一緒に作った戦型も消す。ほかの研究手順がその戦型を記録していれば残す。前からあった戦型を使ったときは消さない。確認の窓に戦型の名前も出す
2. 出発点の初期値は、どの手順にも**出発点より後に自分の手が 1 手以上残る所**まで戻す（「全部が通る最後の局面」が手順の終わりと重なると、定跡帳が ‹ で戻れず、稽古が初手からになるため）。‹ › で終わりまで進めることはできるが、注意書きを出す
3. ［取り消す］の消した記録は、今回足した研究手順だけに効かせる（`onlyId`）。「選んで消す」は 1 本ずつの削除と同じ
4. ［取り消す］は定跡帳の一覧を離れるまで

### 設計案で伝えた作り方（了承済み）
- データの形・バックアップの版は変えない
- 戦型の行は実際に入るグループを出す。分かれるときは「横歩取り 3本・その他 2本」

- 今ある研究手順の自動の名前は、今まで通り次にアプリを開いたときに短くなる
- 定跡帳の ⋯ は「この局面」の欄にボタン。初期局面では押せない

### ツリー生成の仕様（段階1以降）
- **自分**：研究する側（先手か後手かを利用者が選ぶ）。**相手**：もう一方。**相手ノード**：相手が指す番の局面。**自分ノード**：自分が指す番の局面
- 探索するのは原則として**相手ノードだけ**：`go movetime T`（MultiPV=N）→ 各候補の PV の 1 手目＝相手の応手、2 手目＝自分の対応（探索し直さない）→ 自分の対応後の局面を待ち行列へ
- 幅優先。同じ深さでは評価値が良い枝を優先
- 採用条件：最善手から **W 点以内**（初期値 W=300）。N の初期値は 4
- 相手の応手のラベル（しきい値は設定で変更可）：差 0〜50「本線」、51〜150「有力」、151 以上「疑問手（咎められる）」
- 自分の対応（PV の 2 手目）には「未検証」。「この手を検証」でその局面だけ探索し直して確定する
- **v0.4.0〜 プリセットに「自分の対応を調べる時間」（`replyMs`）**：1 以上なら PV の 2 手目は使わず、相手の応手の後の自分ノードを MultiPV=1・replyMs で調べ、確定した手（検証済み）を置く。
  0 なら従来どおり未検証。「ここから展開」では、前の版で作った未検証だけの自分ノードも調べ直す（元の手が違えば「検証前の手」として残る）
- **v0.6.2〜 疑問手の先は浅く**（`GenerationSettings.dubiousCp`＝設定の「有力」のしきい値、初期値 150。持ち主の判断 2026-11-14）：最善手との差がこれより大きい相手の応手は、咎める自分の手（確定または未検証）までで止め、その先の相手の局面は調べない。浮いた時間を本線・有力に回す。
  ほかの手順（本線・有力）からも来られる局面は先まで調べる。「ここから展開」で疑問手の後の局面そのものを選べば先まで調べる。dubiousCp が無いツリー（v0.6.1 まで）は従来どおり。画面では、止めた局面に「相手の疑問手を咎めた後の局面なので…」と案内する（`isAfterDubiousOnly`）
- **段階4-3 A「この手は調べない」（除外、v0.9.0〜、持ち主の判断 2026-11-15）**：相手の応手の行の「⋯」→「この手を除外」。
  除外した手は `TreeNode.excluded` に移す（`edges` から外すので、書き出し・復習・ここから展開・先の局面の数は自動的にたどらない。その先の局面は消さない）。
  除外したらその局面だけをすぐ調べ直す（`TreeGenerator.resample`：ツリーの 1 局面の時間・MultiPV、**`go searchmoves` で除外した手以外の合法手（`legalMoves`）だけ**を調べる）。
  ラベル（diff）は残った手の中の最善手から付け直す（`relabel`）。新しく入った応手の自分の対応は読み筋の 2 手目を未検証で置く。「戻す」は調べ直さずにラベルだけ付け直す。
  生成中は除外・戻すはできない。ツリーをまたいで効く「いつも除外する手の形」は作っていない
  - `go searchmoves` は Windows 版・WASM 版とも効くことを確かめた（WASM 版は Playwright の本物のエンジンでの除外のテスト）
- **段階4-3 B「自分の指したい手で調べる」（v0.10.0〜、持ち主の判断 2026-11-15）**：自分の手番の局面で「別の手を調べる」→ 盤をタップして手を選ぶ → プリセットを選ぶ（`TreeGenerator.explore`）。
  1. 同じ時間（`compareMsOf`＝プリセットの replyMs、無ければ movetimeMs）で、最善手（MultiPV=1）と選んだ手だけ（`go searchmoves <手>`）を調べる
  2. 選んだ手に `userChosen: true` と `loss`（最善手との差、0 以上）を付けて**本線（edges[0]）**にする。エンジンの最善手は消さずにその下（画面の印「最善」）
  3. 選んだ手の後の局面（相手の手番）から、選んだプリセットで展開する（`run` と同じ）
  - **自分ノードに手が複数あるときは、本線（edges[0]）の先だけをたどる**（`collectFrontier`。検証前の手・本線でない自分の手の先は広げない）
  - 自分ノードを調べ直しても（`placeMine`）、本線が利用者の手なら本線はそのまま、最善手はその下。前の最善手が別の手なら「検証前の手」にする
  - 本線は、相手の応手の行の「→ 自分の対応」（印「自分の手」）・復習の正解・KIF の本譜・ここから展開でたどる手になる（どれも edges[0] を使うので自動的にそうなる）
  - 自分の対応の行の「⋯」（手が 2 つ以上のとき）：「本線にする」（`makeMainMove`）、「消す」（`deleteMove`。確認あり・元に戻せない。開始局面からたどれなくなった局面も消す。除外した手の先は残す。最後の 1 手は消さない）。`src/tree/edit.ts`
  - 印は `mineMark`（`src/tree/browse.ts`）：自分の手／最善／検証済み／検証前の手／未検証
- PV が 1 手しかないときは、その応手の後の局面を自分ノードとして探索する
- 詰み（`score mate`）は評価値の大小比較で正しく扱う
- 終了条件：時間の上限・深さの上限（往復の数、初期値 4）・ノード数の上限・利用者の停止。どこで止まっても、それまでのツリーは有効なものとして保存する
- プリセット（`src/tree/presets.ts`。v0.4.0 で見直し、持ち主の判断 2026-11-14）：
  ふつう 2分／相手の局面 1500ms・N=3／自分の対応 1000ms／4往復、じっくり 5分／2500ms・N=4／1500ms／5往復。「さっと」はやめた

  - 設定に v0.3 までのプリセット（replyMs が無い）が保存されていたら、新しい初期値に置き換える（`normalizeSettings`）
  - 残る課題：序盤ではエンジン自身が多くの手を ±50 点以内のほぼ同点と見るため、端歩などの「人があまり指さない手」も応手に入る。深く読んでも変わらない（定跡データなどが必要。未決定）
  - 基準はいちばん遅い Android（4 スレッドで 1 秒あたり約 15〜23 万局面）。スレッド数の初期値は「使える範囲で最大、上限 7」（v0.5.1〜。それまでは上限 4）

  ブラウザではエンジンを分けて同時に動かすと合計の速さが落ち（PC：1×4 で 134 万 → 4×1 で 81 万局面/秒、iPad：1×4 で 125 万 → 2×2 で 117 万）、

- 評価値は**常に自分から見た値**で表示（プラスなら自分が有利）
- 「ここから展開」：任意のノードから同じ処理をプリセットを選んで追加実行し、既存のツリーに枝を足す（`TreeGenerator.run(startKey)`。深さはその局面から数える）

- ツリー生成のロジックはエンジンの実装から切り離し、**モックエンジンでテストできる**作りにする（将来、別エンジンを足せるように）

  - 形式 2（段階4-3 A〜）：局面に `excluded`（除外した手）を足した。形式 3（段階4-3 B〜）：自分の手に `userChosen`・`loss` を足した。
